\chapter{方法与系统实现}

\section{总体架构}

系统总体采用“文档解析-多模态向量化-检索重排-GRPO 决策模型-多模态生成-PDF 高亮溯源”的流程。用户上传 PDF 或图片后，后端首先完成页面解析、页面图渲染、表格识别、局部视觉区域抽取和结构化 chunk 构建；查询阶段，系统通过检索和重排获得候选证据，再由 GRPO 训练得到的决策模型选择更合适的 LLM/VLM 与证据组织方式，最后生成答案并把引用位置映射回前端 PDF 预览界面。

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.95\textwidth]{image/frame.png}
  \caption{系统总体架构图}
  \label{fig:system_architecture}
\end{figure}

如图 \ref{fig:system_architecture} 所示，系统可以分为五个层次：

\begin{itemize}
  \item \textbf{文档解析层}：负责把 PDF、扫描件和图片转换为页面文本、页面图、表格、图像区域和坐标信息，是后续检索与视觉理解的基础。
  \item \textbf{知识索引层}：把 text、table、figure、code 等不同类型的 chunk 统一保存，并为文本、表格 Markdown 和视觉区域建立 embedding。
  \item \textbf{检索重排层}：先通过向量检索召回候选 evidence，再使用 Reranker 对候选证据进行二次排序，减少无关内容进入生成阶段。
  \item \textbf{决策生成层}：通过 GRPO 强化学习训练决策模型，使其根据问题类型、候选证据和历史奖励选择最合适的 LLM/VLM 来回答。
  \item \textbf{前端溯源层}：展示文件、chunk、问答结果和连续 PDF 预览，并根据后端返回的 page、bbox 和 evidence id 在原文档中绘制高亮。
\end{itemize}

这一架构的核心思想是把“回答问题”和“找到证据”同时纳入系统流程。对于纯文本问题，系统主要依赖文本 chunk 和文本生成模型；对于图表、表格、票据、广告和截图类问题，系统会引入页面图、局部 crop 和 VLM；对于边界问题，则由 GRPO 决策模型在候选 LLM/VLM 和上下文组织方式之间进行选择。

\section{文档解析实现}

文档解析模块主要解决“知识从哪里来”的问题。系统需要把用户上传的 PDF 或图片转换为后续可以检索、可以送入模型、可以回到原文档高亮的结构化 evidence。该模块主要由页面解析、区域抽取、chunk 构建和坐标保存四个步骤组成。

\begin{itemize}
  \item \textbf{页面级解析}：对于 PDF 文件，系统使用 PyMuPDF 按页抽取文本，并将每一页渲染为 PNG 页面图；对于图片文件，系统将其视为单页文档处理。解析后，每页都会保留页码、页面文本、页面图路径、页面宽度和页面高度。
  \item \textbf{版面区域抽取}：系统在页面级文本基础上进一步识别普通段落、代码块、表格、图片、图表和公式区域。普通段落形成 text chunk，代码段形成 code chunk，图片和图表区域形成 figure chunk，公式区域可以作为独立视觉 evidence 保存。
  \item \textbf{表格结构化}：表格区域通过 PyMuPDF 的表格检测能力抽取，并转换为 Markdown table。这样做可以保留表格的行列结构，使表格既可以参与文本检索，也可以在生成阶段作为结构化上下文输入。
  \item \textbf{重复内容过滤}：已识别的表格、图片和公式区域会从普通页面文本中排除，避免同一内容既以 text chunk 入库，又以 table 或 figure chunk 重复入库，从而减少检索噪声。
  \item \textbf{坐标与溯源字段}：每个 chunk 都保存 page、bbox、image path、page width 和 page height 等字段。前端在展示证据时，可以根据这些字段把 evidence 映射回原始 PDF 页面。
\end{itemize}

经过解析后，一个文档不再只是普通文本集合，而是由“页面-区域-chunk-evidence”组成的结构化知识库。文本信息用于语义召回，页面图和局部 crop 用于 VLM 视觉理解，bbox 和页面尺寸用于前端高亮。这种设计使 Text-RAG 与 Our-RAG 可以共享同一套文档基础表示。

为了保证后续模块能够稳定使用解析结果，系统在 chunk 层面统一保存以下几类字段：

\begin{itemize}
  \item \textbf{内容字段}：包括 chunk text、OCR text、table Markdown、figure caption 或代码文本，用于检索、重排和 prompt 构建。
  \item \textbf{位置字段}：包括 page、bbox、page width 和 page height，用于把 evidence 从模型输入重新映射到 PDF 页面。
  \item \textbf{视觉字段}：包括 page image path、crop path 和 region type，用于在 VLM 推理时读取局部图像。
  \item \textbf{类型字段}：包括 document id、chunk id、source type 和 modality，用于区分 text、table、figure、formula 和 code 等不同证据来源。
\end{itemize}

这种字段设计避免了“检索时只知道文本，展示时找不到位置”的问题。后端在每次问答中都可以沿着 evidence id 找回原始页面、局部图像和高亮坐标，前端也可以在不理解模型内部逻辑的情况下完成可视化溯源。

\section{Embedding 与 Fusion 实现}

Embedding 模块负责把不同来源的 evidence 转换为可检索的向量表示。系统并不把文本、表格和图像割裂成三个互不相关的库，而是通过统一的 embedding 接口组织多模态证据，使后续检索可以同时考虑语义文本和视觉区域。

\begin{itemize}
  \item \textbf{文本向量化}：文本 chunk、OCR 文本和表格 Markdown 使用 BGE-M3 生成向量表示。BGE-M3 对中文、英文和长文本都有较好的语义表示能力，适合作为文档问答中的基础文本 embedder。
  \item \textbf{表格向量化}：表格不直接以截图形式入库，而是先转换为 Markdown table，再进行文本向量化。这样可以让问题中的行名、列名、时间、数值和单位与表格结构产生语义匹配。
  \item \textbf{图像向量化}：图像侧使用轻量视觉特征或 Native ViT 图像编码器提取视觉向量。视觉向量主要用于保留局部区域、图表形态、页面截图和图片 chunk 的检索能力。
  \item \textbf{向量融合}：统一文本-图像 embedder 会记录 embedding modalities、embedding space 和 evidence type，使文本、表格和图像 evidence 可以进入同一检索流程。
  \item \textbf{证据融合}：一个 evidence 不只包含向量，还绑定文本内容、页码、页面图路径、bbox、OCR 文本、局部 crop、表格 Markdown 和来源类型。生成阶段可以根据这些字段选择更合适的上下文形式。
\end{itemize}

Fusion 在本系统中更偏向工程层面的融合：文本负责语义召回，图像负责补充页面和局部视觉信息，表格 Markdown 负责提供结构化行列关系，坐标字段负责证据溯源。通过这种方式，系统可以在不改变整体检索框架的情况下，把纯文本 RAG 扩展为能够处理图片、表格和图表的多模态 RAG。

索引构建阶段，系统会先将所有 chunk 转换为统一 evidence 对象，再根据 evidence type 调用不同的向量化逻辑。文本和表格直接进入 BGE-M3；图像区域会先读取局部 crop 或页面图，再生成视觉特征；对于同时含有 OCR 和图片的 evidence，系统会保留文本向量和图像向量的来源信息，并在 metadata 中标注其融合方式。这样做的好处是，后续消融实验可以单独关闭统一多模态向量化，观察它对结果的影响；同时也方便在真实部署中替换更强的视觉 encoder，而不需要改动检索和前端溯源逻辑。

\section{向量检索与 Reranker 实现}

查询到来后，系统首先将用户问题编码为查询向量，并在 FAISS 索引中召回 Top-K 候选 evidence。初步召回的结果通常包含相关 chunk，也可能包含部分语义相近但证据不足的片段，因此需要 Reranker 进一步控制输入生成模型的证据质量。

\begin{itemize}
  \item \textbf{粗召回}：系统根据查询向量从知识库中召回候选 evidence。候选结果包括普通文本、表格 Markdown、图像区域和页面相关 OCR 片段。
  \item \textbf{二次重排}：系统使用 BGE-reranker-v2-m3 对“问题-候选证据”进行交叉编码打分，重新排序候选 evidence。Reranker 可以更细致地判断问题与证据之间的语义关系。
  \item \textbf{证据筛选}：重排后仅保留分数较高的 evidence 输入生成阶段，避免无关 chunk 干扰模型回答。对于图表或票据类问题，重排结果还会影响后续视觉区域的选择。
  \item \textbf{引用编号}：进入 prompt 的证据会被整理为 [E1]、[E2] 等编号。模型在回答中引用证据编号，后端再把编号映射为具体页码、chunk id 和 bbox。
\end{itemize}

Reranker 在系统中的作用不只是提高文本答案质量，也会影响 VLM 能否看到正确的视觉区域。例如，问题涉及图表数值时，文本检索会先帮助系统定位相关页面或图表标题；问题涉及广告品牌、票据字段或日程表时，检索结果会帮助系统找到 OCR anchor，再由视觉区域模块裁剪局部 crop。检索、重排和视觉裁剪之间形成了一个连续的证据定位流程。

在上下文构建时，系统不会简单把 Top-K 结果全部拼接给模型，而是根据 evidence type 和问题类型进行筛选。普通文本问题优先保留语义分数最高的段落；表格问题优先保留表格 Markdown、表头和相关行；图表问题优先保留图表区域、页面标题和局部 crop；票据或广告问题则优先保留包含字段名、品牌名和局部视觉区域的 evidence。这样可以在有限上下文长度内提高有效信息比例，也减少 VLM 同时处理多张无关页面图带来的成本。

\section{GRPO 决策模型实现}

GRPO 决策模块对应架构图中的强化学习训练闭环。它的核心不是把路由规则写死，而是训练一个 Decide Model，让它根据用户问题和检索到的 evidence，选择更合适的 LLM/VLM 来回答。不同模型分别生成答案后，再由 Judge Model 对答案质量打分，最后使用 GRPO 根据 reward 更新 Decide Model。

如图中所示，训练流程可以概括为四个步骤：

\begin{itemize}
  \item \textbf{Decision Model 选择模型}：Decide Model 接收问题、检索证据和问题类型信息，选择若干候选回答模型，例如文本 LLM、多模态 VLM 或图表增强 VLM。
  \item \textbf{候选模型生成回答}：被选择的候选模型分别根据同一个问题生成答案。普通文本问题可以由文本 LLM 回答，图表、票据、广告和页面区域问题则更依赖 VLM。
  \item \textbf{Judge Model 评分}：Judge Model（如 Qwen-Max）对候选答案进行评估，根据答案是否正确、是否符合证据、是否回答完整给出 reward，例如 0、0.5 或 1。
  \item \textbf{GRPO 更新 Decide Model}：系统根据不同候选答案的 reward 使用 GRPO 更新 Decide Model，使高分模型选择在后续相似问题中更容易被采用。
\end{itemize}

因此，GRPO 决策模型在系统中的作用可以理解为“学会选模型”。它不直接替代检索、Reranker 或 VLM 推理，而是在它们之上决定当前问题应该交给哪个模型回答。对于纯文本问题，Decide Model 更倾向于选择文本 LLM；对于图表数值、票据版面、广告标签和局部视觉区域问题，Decide Model 更倾向于选择多模态 VLM。随着 Judge Model 的评分反馈不断积累，Decide Model 可以逐渐形成更稳定的模型选择策略。

\section{多模态生成与局部视觉证据实现}

生成阶段接收检索重排后的 evidence 和 GRPO 决策模型输出的模型选择结果，组织文本、表格 Markdown、页面图和局部 crop，由相应的 LLM/VLM 生成答案。系统使用 Qwen3-VL-8B-Instruct 处理需要视觉理解的问题，并通过 prompt 约束模型给出短答案、证据编号和可溯源引用。

\begin{itemize}
  \item \textbf{上下文重构}：系统根据问题类型和决策结果选择 evidence。如果问题主要依赖文本，就优先拼接文本 chunk；如果问题涉及表格，就加入 Markdown table；如果问题需要视觉判断，就加入页面图或局部 crop。
  \item \textbf{局部区域生成}：系统根据 OCR bbox、问题关键词、表格/图片 metadata 和检索结果生成候选 crop。与整页输入相比，局部 crop 可以减少视觉 token 成本，也能降低页面其他内容对 VLM 的干扰。
  \item \textbf{图表问题处理}：对于 ChartQA 类问题，系统优先裁剪图表主体区域，并在 prompt 中强调坐标轴、柱高、折线趋势、最大值、最小值和差值比较等任务信息。
  \item \textbf{表格问题处理}：对于表格行列关系问题，系统同时提供表格 Markdown 和局部页面图，使模型既能看到结构化文本，也能参考原始版面。
  \item \textbf{答案与引用输出}：模型生成答案后，后端保留 evidence id、页码、chunk id、bbox 和来源类型，前端据此完成 PDF 高亮。
\end{itemize}

局部视觉区域的作用不是简单地“多给模型一张图”，而是把 VLM 的注意力集中到高价值证据上。对于广告品牌、票据字段、商品标签、课程表时间段和图表数值等问题，纯文本 OCR 往往会丢失空间关系或视觉实体信息；局部 crop 可以补充这些信息，使模型更接近人在阅读 PDF 页面时的判断方式。

生成完成后，系统还会进行轻量答案后处理。对于评测任务，后端会抽取短答案，去除多余解释句，并对大小写、空格、标点、单位和数值形式进行归一化；对于图表数值题，系统允许一定范围内的数值容差；对于 Yes/No 问题，系统会优先提取明确的肯定或否定词。后处理不改变模型推理结果，只是把生成式输出整理为更稳定的答案形式，便于评测脚本计算 EM、ANLS 和 Answer Match。

同时，答案后处理会保留引用证据与页面位置。模型输出的 evidence 编号会被解析为后端内部的 chunk id，再关联到 page、bbox、source type 和 image path。这样即使答案文本经过归一化，前端仍然可以展示原始证据位置，用户也能回到 PDF 页面检查模型是否引用了正确区域。

\section{前后端交互与 PDF 预览实现}

系统使用 FastAPI 实现后端服务，并使用 React、Vite、TailwindCSS 和 Framer Motion 构建前端界面。FastAPI 负责封装文件上传、解析任务、chunk 查询、页面图读取、检索问答和文件删除等功能；前端负责展示文件列表、知识库 chunk、问答窗口和连续 PDF 预览。

\begin{itemize}
  \item \textbf{文件与解析状态}：用户上传文件后，后端维护 uploaded、queued、parsing、ready 和 failed 等状态，前端通过轮询展示解析进度和错误信息。
  \item \textbf{知识库浏览}：解析完成后，前端展示 chunk 类型、页码、文本摘要和来源信息，用户可以直接点击 chunk 查看对应 PDF 区域。
  \item \textbf{问答交互}：用户提交问题后，后端返回答案、引用 evidence、页码和 bbox。前端在答案区展示引用，同时联动右侧 PDF viewer。
  \item \textbf{连续 PDF 预览}：右侧预览区不是单独显示某个 chunk，而是连续展示整个 PDF 页面，用户可以上下翻页检查文档上下文。
  \item \textbf{区域高亮}：当用户点击 chunk 或答案引用时，前端根据 page、bbox、page width 和 page height 计算缩放比例，并在对应页面上绘制高亮框。
\end{itemize}

PDF 高亮的关键在于坐标变换。后端保存的 bbox 使用解析阶段的原始页面坐标，前端展示时页面会根据容器宽度缩放，因此需要根据渲染后的页面宽高重新计算比例。具体而言，前端先找到 evidence 对应页，再读取该页的原始宽高和当前显示宽高，分别计算 x 与 y 方向的缩放系数，最后将 bbox 的左上角和宽高映射到页面图上的绝对位置。这样无论用户在桌面端还是较窄窗口中查看 PDF，高亮框都能落在相同的文档内容区域。

这种前端设计使系统的证据展示方式更接近真实知识库产品：用户不仅能看到模型答案，还能看到答案对应的原文档区域。当模型回答存在疑问时，用户可以直接回到 PDF 页面检查上下文，从而提高系统的可解释性和可验证性。
